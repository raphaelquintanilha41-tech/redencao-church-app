Redenção Church App — Auditoria e Especificação Consolidada

O que existe, o que falta, e o que precisa de backend real

Contexto importante: este projeto é um protótipo de front-end interativo (clicável), sem banco de dados, servidor, autenticação real ou painel administrativo funcional. Itens como RLS, permissões por papel, logs de auditoria, backup, push notifications reais e conformidade RGPD não existem — e não podem existir — neste tipo de entrega. Esta auditoria classifica cada área pedida e, quando aplicável, aponta para os documentos técnicos já produzidos (Especificação Técnica - Perfil.dc.html e Especificação Técnica - Igreja.dc.html) ou detalha aqui o que falta.

2. O que exige backend real (não implementável em protótipo de design)

Os documentos Especificação Técnica - Perfil.dc.html e Especificação Técnica - Igreja.dc.html já cobrem: modelo de dados, autenticação, upload de foto, RLS/segurança, sincronização entre dispositivos, painel administrativo por área. Este documento adiciona os pontos do novo briefing que ainda não estavam cobertos.

2.1 Permissões por papel (RBAC)

PapelAcesso
Super AdminTudo
PastorConteúdo, membros, pedidos de oração, acompanhamento pastoral
AdministradorConteúdo e eventos
EditorPublicação de conteúdo (Palavra do Dia, devocionais, banners)
Líder de CélulaSomente a própria célula e seus interessados
Líder de MinistérioSomente o próprio ministério e seus interessados
IntercessorPedidos de oração autorizados (não confidenciais salvo autorização extra)

Implementar via claims/roles no backend de autenticação + RLS por papel — nunca apenas ocultar botões na UI.

2.2 Controlo editorial e agendamento

Aplicar aos conteúdos de Palavra do Dia, Devocionais, Notícias, Eventos e Banners um campo status: draft → review → scheduled → published → archived, mais publish_at e expire_at para agendamento. Um job periódico (cron/edge function) promove scheduled → published quando chega a data.

2.3 Logs administrativos (audit_logs)

Tabela audit_logs (actor_id, action, resource_type, resource_id, before, after, created_at) registando toda alteração feita por um papel administrativo — essencial para rastreabilidade em conteúdo pastoral sensível (pedidos de oração, testemunhos, batismos).

2.4 RGPD (aplicação usada em Portugal)

  • Política de Privacidade e Termos de Utilização versionados, com aceite registado por usuário e data.
  • Exportar dados pessoais (JSON/PDF) e excluir conta com confirmação — a exclusão deve remover ou anonimizar notas, favoritos, histórico e pedidos de oração, preservando apenas o necessário para registos pastorais com base legal (ex.: contabilidade de ofertas, se aplicável).
  • Consentimento explícito e retirável para: notificações, uso de fotografia em testemunhos, contacto de "Sou Novo Aqui".
  • Minimização de dados: não recolher campos que a funcionalidade não usa (ex.: data de nascimento no batismo só se for estritamente necessária).
  • Atenção redobrada a: pedidos de oração, dados de visitantes, inscrições de batismo, participação em células, e qualquer dado sobre crianças (nunca criar perfil de conta própria para menores nesta fase — apenas visibilidade de horários/avisos para responsáveis).

2.5 Notificações push

Serviço de push (ex. FCM/APNs via backend) com tabela device_tokens por usuário, categorias de notificação (Palavra do Dia, Devocionais, Cultos, Eventos, Planos, Cursos, Igreja) e preferências individuais já modeladas na UI de Perfil. Cada notificação carrega um deep link (ex. /biblia/joao/3, /evento/123) que a app resolve ao abrir.

2.6 Deep links e busca

Definir rotas estáveis para Bíblia, devocional, evento, pregação, célula. A busca global do protótipo já demonstra o padrão de resultado tipado (Bíblia/Mensagem/Evento) — o backend real estenderia a mesma busca a devocionais, planos e cursos via full-text search.

2.7 Segurança geral

Nunca expor chaves de serviço (service role) no cliente; variáveis sensíveis apenas em ambiente de servidor; rate limiting em endpoints de formulário público (pedidos de oração, "Sou Novo Aqui", testemunhos) para evitar abuso; upload de imagens validado por tipo/tamanho antes de ir para storage.

2.8 Banco de dados

Reaproveitar as tabelas já listadas nos dois documentos anteriores (profiles, favorites, bible_notes, reading_history, prayer_requests, cells, ministries, baptism_requests, testimonies, church_events, giving_methods, etc.) — não duplicar. Adicionar apenas: audit_logs, device_tokens, notification_preferences (já prevista), consents (RGPD), reading_plans / reading_plan_progress. Toda alteração de schema via migration versionada, nunca manual.

3. Instalação como PWA + notificações + badge de ícone

Implementado no protótipo (Perfil → Configurações → seção "Aplicação" e nova tela "Instalar Redenção Church"): detecção de display-mode: standalone, captura real de beforeinstallprompt (Android/desktop) com chamada a prompt(), instruções visuais dedicadas para iOS (Safari → Compartilhar → Adicionar à Tela de Início, sem botão falso), Notification.requestPermission() só acionado por toque explícito do usuário (nunca automático), e badge no ícone via navigator.setAppBadge()/clearAppBadge() com feature detection — sincronizado ao contador de notificações não lidas já existente no protótipo.

4. Plano de implementação (para a equipa de desenvolvimento)

  1. Fase 1 — Crítica: autenticação real, banco de dados, RLS, permissões por papel, segurança de pedidos de oração, RGPD básico (política, consentimento, exportar/excluir dados).
  2. Fase 2 — Alta: Bíblia com tradução licenciada e busca, sincronização de favoritos/notas/histórico, Palavra do Dia e Devocionais com publicação agendada, Agenda ligada a banco.
  3. Fase 3 — Média: Dízimos, Células, Próximos Passos, Quero Servir, Batismo, notificações push reais, busca global no backend.
  4. Fase 4 — Expansão: Cursos/Discipulado, Biblioteca, Redenção Kids, métricas avançadas, modo offline.

5. Testes de fluxo recomendados (para QA da equipa técnica)

Novo visitante (onboarding → visitante → Home → Agenda → Sou Novo Aqui); novo membro (cadastro → Bíblia → favoritar → Perfil); pedido de oração (enviar → painel → status → usuário consulta); célula (solicitar → aprovação → aparece em Minha Redenção); evento (abrir → inscrever → Perfil); Palavra do Dia (notificação → abrir → ler → favoritar). Estes fluxos já são navegáveis ponta a ponta no protótipo de UI, exceto pelas partes que dependem de backend (aprovação administrativa, notificação push real).
